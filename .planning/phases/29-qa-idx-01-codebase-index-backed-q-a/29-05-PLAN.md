## Flagged Assumptions (unresolved edge — do not treat as settled)

The deterministic edge probe for QA-IDX-01 returned exactly one applicable edge, in the
**concurrency** category, with status `unresolved`: *"If interrupted or run in parallel, what is
guaranteed?"* There is no SPEC.md for this phase, so nothing resolved it upstream. It is surfaced here
rather than dropped, because this plan is where interruption and concurrency actually live: an index
build is a long-running Workflow instance that can hibernate mid-run, be superseded by a newer push,
or race a second trigger for the same repository.

What this phase guarantees, as designed — each clause is implemented by a task in this plan or 29-04
and pinned by a named spec case, so the guarantee is checkable rather than asserted:

- **Under interruption**, no partial work is lost and none is redone: per-file progress is committed to
  `code_index_files` as each file completes, `listIndexedPathsForSha` is read at the *in-progress* sha
  before the file loop, and `indexed_sha` on `code_index_state` is advanced only by
  `markCodeIndexBuildCompleted`. A build killed at any point therefore resumes from the next unindexed
  path and never claims a commit it did not finish.
- **Under concurrency**, at most one build is live per repository: `claimCodeIndexBuildLease` is a
  single conditional statement, so two simultaneous triggers cannot both win, and the loser performs no
  work and reports a coalesced outcome. The stable per-repository workflow instance id makes
  `instance.already_exists` a second, independent coalescing layer.
- **Under a crashed owner**, the lease expires rather than wedging the repository forever, and release
  resolves `status` back to `idle` so the panel does not show a phantom live build.

What is **not** guaranteed, and is accepted rather than solved: a build is not superseded by a newer
push mid-run. A push that lands while a build holds the lease is coalesced away, so the finished index
reflects the commit the build started from, not the newest one. Freshness then depends on the next push
event. This is a deliberate simplification of the review path's supersede check — the review path
supersedes because a stale review is *wrong*, whereas a slightly stale index only makes retrieval
slightly stale, and D-15 already fails Q&A open on staleness. Recorded so the absence of a supersede
check is visibly a choice.
