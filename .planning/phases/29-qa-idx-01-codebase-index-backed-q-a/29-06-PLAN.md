<objective>
Add default-branch push handling on both providers so a merge to the default branch refreshes only the changed files, and fix the Bitbucket route's identity contract, which currently rejects a `repo:push` delivery before it is ever verified.

Purpose: without freshness the index is a one-shot snapshot that silently rots. This is also the one place in the phase where the "additive" framing in the decision does not hold: the Bitbucket route's step-3 identity projection hard-requires a pull request, and three later steps read pull-request fields unconditionally, so `repo:push` returns 400 today — before the HMAC verify.

Output: `push` added to the GitHub supported-event list with a route branch that returns before the pull-request tail; a `repo:push` union member plus an event-aware identity projection on the Bitbucket route with its verification ordering untouched; and one spec covering both providers including the regression guard that would fail against today's code.
</objective>

## Flagged Assumptions (A1 / A2 — unvalidated external payload shapes)

Both reviewers independently rated this the **top risk in the phase**, and it is the one thing more
planning cannot close — only a real delivery can. Recorded here, in the plan that owns both payloads,
so it is visible to whoever executes rather than buried in a review file.

- **A1 — GitHub `push` payload's `repository.default_branch`.** Not documented for the push event.
  Mitigated by reading `default_branch ?? master_branch` and skipping when both are absent. The residual
  risk is a *silent* skip, which Task 1 now closes with a warning log.
- **A2 — Bitbucket `repo:push` payload's `push.changes[]` shape.** Community-sourced; the official docs
  page is truncated. Mitigated by `z.looseObject` so an unexpected extra field does not fail the parse.
  The residual risk is a *field-name* mismatch (for example `new.target.hash` versus something else),
  which degrades to a parse failure and an ignored acknowledgement — a silent no-op that looks exactly
  like a correctly-ignored delivery.

Both reviewers recommended capturing one real delivery **per provider before merging this plan**,
rather than relying on 29-09's end-of-phase human-verify gate alone. That recommendation is adopted as
Task 4 of this plan.
