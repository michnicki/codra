Comment the two deliberate departures from house precedent: the composite primary key instead of a surrogate `id` plus `UNIQUE`, chosen because it is the index the delete-changed-paths refresh scans; and `ON DELETE CASCADE` from `repositories(id)`, unlike the non-cascading `repository_id` references in `001_initial.sql`, because the index must be deleted with the repository. Comment that `search_vector` is written by the application rather than `GENERATED ALWAYS AS ... STORED` specifically so the JS byte cap runs before the insert, and that the narrow `repository_id` btree exists in addition to the primary key because the planner was measured to ignore the primary key and sequentially scan when one repository dominates the table. Document the four `status` values `idle`, `building`, `ready`, `failed` in a comment.

Two further comment blocks the migration must carry, both raised by cross-AI review (see the disposition table above).

Document the `code_index_files.skip_reason` token vocabulary in a comment on that column: the writer emits exactly one of `empty`, `generated`, `oversized`, `unreadable`, and a `NULL` means the file was indexed normally. State in the same comment that this is deliberately a documented vocabulary and **not** a `CHECK (skip_reason IN (...))` constraint, because a `CHECK` would turn adding a future skip reason into a schema migration on a column whose only consumer is the resumability read, and because the column is written from exactly one accessor (`markCodeIndexFileIndexed`) whose own contract already restricts it to a short machine token — a constraint would buy enforcement the single writer already provides while costing a migration per vocabulary change.

Document the `code_index_state.mode` values in a comment: `full` for a dashboard-triggered rebuild and `incremental` for a push-triggered refresh, `NULL` before the first build. State that this column is the operator-facing answer to "what produced the current index" and is read by the status endpoint and rendered by the dashboard panel, so it must be written on every build start, not only on completion.

Export `CODE_INDEX_PATH_WEIGHT = 'A'` and `CODE_INDEX_CONTENT_WEIGHT = 'D'` as const, with a rationale comment recording the measured facts: `ts_rank_cd`'s weight array is ordered `{D, C, B, A}` so the defaults `{0.1, 0.2, 0.4, 1.0}` mean `D=0.1` and `A=1.0`, and a path-token hit was measured to outrank a body-only hit by 10x with no post-processing (D-04). Export `CODE_INDEX_MAX_CHUNK_BYTES = 32_768` with a rationale comment stating that `to_tsvector` raises above roughly 1 MB of resulting vector (a 1 088 889-byte input produced a 1 477 980-byte vector against a 1 048 575-byte ceiling), that a real 50-line window measured 2 854 bytes, and that without this cap one window of a generated or minified file hard-fails the whole build step and then burns the Workflow retry budget re-throwing deterministically. The same comment must record the review measurement that fixes this value in place: on the live PG 17.10 test database a 32 KB chunk of maximally dense *unique* camelCase identifiers, plus the pre-split tokens `buildIndexTokens` appends, produced 71.8 KB of combined input and a **134 KB tsvector — 12.8% of the 1 048 575-byte ceiling**, and even at double the cap the vector reached only 25.3%; real minified JavaScript has longer tokens and therefore *fewer* lexemes, so that is close to a worst case. State plainly that the value must therefore **not** be lowered to 16 KB and that no `pg_column_size` guard is warranted, so a future reader does not "harden" away 8x of measured headroom. Export `CODE_INDEX_MAX_FILE_BYTES = 1_000_000` with a comment that a file above this size is recorded as skipped rather than chunked. Export `CODE_INDEX_MAX_QUERY_TERMS = 32` with a comment bounding the query expression a hostile question can produce.

Give the module one module-private `splitIdentifier(token)` that splits camelCase boundaries, snake_case, kebab-case and dot boundaries into lowercase `[a-z0-9]+` component words, using literal character classes with no attacker-constructible regex. Export `buildIndexTokens(path, content)` returning `{ pathTokens, contentTokens }`: `pathTokens` is the raw path followed by its split component words, because `to_tsvector('english', 'src/server/core/code-index.ts')` was measured to produce exactly one unsearchable lexeme while the pre-split form produces the individual words, and feeding both keeps exact-path queries working too; `contentTokens` is the content followed by the split component words of the identifiers found in it, so `getUserById` is reachable from a question about user lookup (D-02).
