must_haves:
  truths:
    - "drop-before-dedup: a hard-dropped finding does not participate in dedup. When a dropped finding and a kept finding have identical content, only the kept finding reaches dedup — no collision or merge ambiguity."
    - "When all findings in a file are hard-dropped, the file produces zero posted findings. The audit event still fires with droppedCount > 0 and a populated sample, so the drop is explainable even when output is empty."
    - "Hard-drop is a filter (in-memory removal before dedup), not a reorder. The relative order of surviving findings is preserved because the drop iterates the findings array and removes non-matching entries in place."
    - "The hard-drop check is deterministic: same diff haystack + same findings produce identical drop decisions. Same deterministic whitespace-collapsed substring search as EVID-01."
    - "The hard-drop is an in-memory filter in the finalize phase. Retries re-run against immutable file_reviews producing identical results. Audit event uses at-most-once gating (same pattern as evidence_missing_summary) to prevent duplicate events on retry."
  prohibitions:
    - "The hard_drop_exempt_categories check MUST compare categories case-insensitively. A config entry 'Security' or 'SECURITY' must match the reviewCategories value 'security'. A case-sensitive comparison would silently bypass exemptions."
